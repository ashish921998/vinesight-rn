How a record can end up with a null season_id

Track A — make season numbers trustworthy

A1 · Recompute assignments when a season starts Small Done

src/hooks/use-farm-seasons.ts — useStartFarmSeason (line 136)

Today only useEndFarmSeason recomputes. A backdated season start (common: farmer starts logging days after pruning) leaves earlier orphaned records null. Fix: in useStartFarmSeason's success path, fire recompute_farm_season_assignments (RPC with the existing recomputeSeasonAssignmentsClient fallback, same pattern as useRecomputeFarmSeasonAssignments:283), then reuse its record-query invalidation block — extract that block into a shared helper rather than duplicating the 10 invalidateQueries calls.

Accept: add an expense dated 2026-06-20 to a farm with no active season → start a season backdated to 2026-06-15 → expense's season_id is set and it appears in that season's report without manual recompute.

A2 · Stop lazy-creating seasons for between-seasons farms Small Behavior decision Done

src/hooks/use-farms.ts — ensureInitialFarmSeason (line 80); called from resolveOrCreateSeasonIdForDate (season-context.ts:143)

Latent bug found while planning (now fixed): ensureInitialFarmSeason used to check only for an active season. A farm whose season just ended has none — so saving any record silently started a brand-new season with start_date = date_of_pruning ?? today. The pruning date is from the previous cycle, so the new "active" season could overlap every ended season and swallow historical records on the next recompute.

Fix landed: only auto-create when the farm has zero seasons (the original intent — old farms predating the feature). If ended seasons exist, the record stays unassigned — A3 makes that visible, A1 heals it when the real next season starts.

Accept: end a season, log an irrigation → no new farm_seasons row appears; record has null season_id. A brand-new farm with no seasons still gets its initial season on first save.

A3 · Surface unassigned records in reports Medium Done

src/components/screens/reports/report-filters-panel.tsx (season section ~line 460 and ~920), app/reports.tsx, src/hooks/use-reports.ts; strings in src/i18n/locales/{en,hi,mr}.ts

When a specific season is selected, DB queries filter eq('season_id', …) — null rows vanish with no trace. Add a lightweight count query (one head: true, count: 'exact' per record table where farm_id = X AND season_id IS NULL, summed in a small useUnassignedRecordCount(farmId) hook) and render a notice row under the season picker when a season is selected and count > 0: "N records aren't in any season — visible under All seasons." Tapping it switches the picker to All seasons.

Deliberately notice-only, no "include them anyway" toggle in season mode: merging unassigned rows into a specific season's totals would misattribute them. The existing includeUnassigned logic already handles All-seasons mode correctly (default true).

Accept: farm with 3 between-season expenses → select a season in reports → notice shows "3 records…"; switch to All seasons → they're in the totals.

A4 · Between-seasons captions for expense/harvest tiles on farm details Small Done

app/farm/[id].tsx — seasonExpenseTotal:422, seasonHarvestQuantity:441, caption pattern at waterUsageCaption:492; strings in en/hi/mr

Closes the TODOS.md P3 item directly. The tiles clamp to [seasonMetricsStartDate, seasonMetricsEndDate]; when the farm is between seasons, entries dated after end_date are excluded silently. Compute the excluded count inside the same memos (records with date > seasonMetricsEndDate) and reuse the existing betweenSeasonsHint caption pattern the water tile already has: "+N logged after season end — not counted." While there, sanity-check isBetweenSeasons:362 — its today < minimumSeasonStartDate condition looks like it's false for most genuinely-between-seasons farms; the new captions should key off "no active season && ended seasons exist" instead.

Accept: end season, add an expense → expense tile shows the excluded-count caption instead of a silently smaller total.

Track B — surface the comparison

The hard part — baseline resolution aligned by days-since-season-start, delta math, double-fetch plumbing — is already built and running (useReportComparison). Track B is exposure: let the user pick the baseline, show more than chips, and put it in the export.

B1 · User-picked comparison season Medium

src/types/report.ts:69-81 (types exist), src/services/report-comparison.ts (resolveBaseline), report-filters-panel.tsx, app/reports.tsx filter state

Wire the dormant ReportFilters.compare?.baselineSeasonId: when a season is selected, show a "Compare with" row in the filters panel — options: Previous season (auto) [default, current behavior], each other season by label (formatReportSeasonLabel), and Off. In resolveBaseline, when an explicit id is set, use that season instead of "the one immediately before", keeping the elapsed-window clamp exactly as-is. compare.enabled: false short-circuits to null (chips disappear — already handled by comparison being null).

Accept: pick season 2024–25 as baseline for 2026 → chips recompute against it; Off hides chips; default unchanged.

B2 · Side-by-side comparison section in the report body Medium

New src/components/screens/reports/report-season-comparison-section.tsx, consuming the (now fully populated) ReportComparison from useReportComparison in use-reports.ts

Delta chips answer "up or down"; consultants need the actual numbers. ReportComparison already carries the baseline's ReportSummary, baseline/current labels, and the elapsed-days window (populated in useReportComparison) — this task is UI-only. New section (rendered with the other report-section-block sections): a three-column table — metric · current season · baseline season · Δ% — over the seven existing comparison metrics (COMPARISON_METRIC_FIELDS in report-comparison.ts:27), with the footnote "Both seasons measured over their first N days." That footnote is the honesty guarantee — without it a partial season looks like a collapse.

Accept: season selected with a prior season having records → section renders with real numbers and the day-window footnote; hidden when comparison is null.

B3 · Comparison in the exported PDF Medium

src/services/report-service.ts — exportPDF (line 1713) and its HTML template; useReportExport in use-reports.ts:358; call sites in app/reports.tsx

The PDF is the consultant's deliverable, and today it carries zero comparison data. Thread an optional comparison block (same extended ReportComparison shape from B2) through exportPDF/downloadPDF and render the same table + footnote in the PDF HTML. CSV stays as-is. Keep the param optional so all existing call sites compile untouched.

Accept: export a season report with an available baseline → PDF contains the comparison table; export with comparison off → PDF unchanged from today.
