Vinesight RN · Implementation Plan · vinesight-rn-clean

One unit contract: kernel, search-select with history, and meticulous reports

2 July 2026 · Status: draft for review · Scope: farmer app (spray + fertigation logging, plan reading) and professional module (plan authoring) · Schema changes deferred to Phase W (web-owned DB)

Today, quantities live as free-typed unit strings interpreted by three drifting alias tables, product names are free text with no identity, and every computation (farmer's "how much do I pour", reports' per-acre totals) re-derives meaning heuristically. This plan replaces that with one unit kernel (measure × basis, display scales on top), one SearchSelect component (history first, catalog second, identity always) used by all three add-item flows, and a reports contract with golden test vectors for per-plot, per-acre, and per-liter computations. Grounded in the ICAR-NRC Grapes 2025-26 annexure dose formats.

2The unit kernel — one module owns meaning

New file src/constants/quantity-kernel.ts (replaces UNIT_ALIASES; units.ts sets become internal to it).

Every quantity in the system is a point on a 2×3 grid, plus a display scale that is presentation only:

type Measure = 'mass' | 'volume' | 'count'; // count = fold-only (pcs/packet/bag) — never a chip
type Basis   = 'total' | 'per_acre' | 'per_liter_water';
type Scale   = 'mg' | 'g' | 'kg' | 'ml' | 'L';   // display/entry only — never identity

// A stored quantity, canonicalized:
interface Quantity { value: number; measure: Measure; basis: Basis }
// ppm is sugar: { measure:'mass', basis:'per_liter_water', scale:'mg' }
// — 1 ppm = 1 mg/L holds for w/v spray/fertigation solutions ONLY. Soil/petiole
//   lab ppm is mg/kg (w/w) and must never route through this kernel.
FunctionContract
parse(unitString, value)→ { quantity, factor } | null. Understands every legacy spelling ('g/acre', 'gram/acre', 'litre', case variants, plurals) via a factor (500 'g/acre' → 0.5 kg-mass per_acre). Also accepts source-only bases: any /ha spelling (annexure label claims, web-written data) normalizes to per_acre with factor ÷2.47105 — the whole app runs on acres; /ha is never a farmer-facing chip and never stored on app-authored records. Returns null for unknowns — never silently kg. Dev builds warn.
format(quantity, locale)Picks the human scale: < 1 kg → g, < 1 g → mg, < 1 L → ml; integers preferred; ≥ 1 → kg/L with ≤ 2 trimmed decimals. Localized unit labels (किलो / ग्रॅम / लिटर / मिली). "≈" prefix when the value was derived (multiplied), never on entered values.
totalFor(quantity, ctx)per_acre × ctx.areaAcres, per_liter_water × ctx.waterLiters, total pass-through → a total Quantity. Returns null when ctx is missing (no area / no water volume) — callers fall back to showing the rate, never guess.
fold(quantity)Analytics currency: everything to canonical kg / L (+ basis carried alongside). Replaces the ad-hoc normalizer inside report-service.ts.
storedUnitString(measure, basis, scale)The only writer of unit strings. Canonical vocabulary is closed: plans → kg/acre · kg · L/acre · L · ppm; logs keep the farmer's chip string (testimony, §3).
Provable, not hoped-for
Canonical spellings are derived from one table at module init (reverse map, lowercased once). The property test in §9 round-trips every chip through store → parse → format and asserts identity. Editing the table cannot desync a second table, because there is no second table.

3Chip vocabulary per surface — basis fused into the chip, no toggles

Validated against ICAR-NRC Grapes Annexure-5 (17 Sep 2025): real doses are ~50/50 concentration (g/L ×24, mL/L ×18) vs per-area (mL/ha ×23, g/ha ×16); ppm appears only for PGRs (GA3, NAA, CCC); the annexure itself writes 5000 g/ha, never 5 kg/ha — spray stays gram-scale by convention. Note the annexure's per-area basis is hectare; the app is acre-only — conversion (÷2.47105) happens once, at the catalog-claim boundary (§11.1), so no /ha chip exists anywhere below.

Live computed line — the error check that doubles as spoon-feeding
Under every dose input where context exists: spray 30 g/L × 400 L = 12 kg in the tank; plan/fertigation per-acre 250 ml/acre × 3.5 acres ≈ 875 ml for your plot; ppm 100 ppm × 400 L = 40 g in the tank. Farmer verifies against the scoop in his hand before saving.
The basis standard: per-acre is the canonical lens, never the forced entry
Entry accepts whichever basis the farmer actually measured (forcing per-acre entry would make a farmer who dissolved "10 kg in the tank" type 10 against a per-acre chip — a silent 3.5× error; and partial-plot fertigation makes "per acre of what" ambiguous). Standardization happens one layer up: (a) defaults — plan quick-add preselects the per-acre chip, manual add defaults to total (bare kg/L), last-used-per-product overrides both; (b) live echo — every entry shows its conversion in the other basis (10 kg → ≈ 2.9 kg/acre, 3 kg/acre → ≈ 10.5 kg total), which also lets the farmer eyeball his plan target with zero arithmetic; (c) downstream — reports, compliance deltas, and every consultant-facing view render per-acre (with totals alongside), derived by the kernel. Standard where comparison happens; freedom where the ground truth lives.
Guardrail: the ml↔L / g↔kg flip
On save, if the entered amount is ~10× or ~1000× off an independent reference — the linked plan item, or the last log for this product — one localized prompt: "योजनेत 875 ml आहे — युनिट तपासा?" Non-blocking (farmer can confirm), telemetry-counted. The live "= in tank" line above is a visual check only, not a guardrail reference: it is computed from the very input being validated, so it can never contradict it. With no plan link and no prior log, the guardrail is honestly inert — first-ever logs rely on the visual line.

The consultant → farmer name loop is closed by the plan, not the catalog
Both roles search the same master catalog, so a catalog-sourced prescription is findable by the farmer verbatim. When the consultant uses the custom escape hatch (name not in catalog), that name still reaches the farmer through the active-plan-items source above — the farmer's picker lists it with the prescribed dose, and selecting it stamps plan_item_id (the same write as one-tap log from the plans screen; two entry points, one mechanism). Identity is the report's foundation — and where it can persist today
Reports group by product. Free text ⇒ "19:19:19" vs "19-19-19" are two rows and the totals lie. Every path through SearchSelect emits { name, product_id?, warehouse_item_id?, is_custom } — but persistence differs by record type and level: spray/fertigation log items already carry item-level identity (catalog_product_id, warehouse_item_id — database.ts:138-146, 190-191; warehouse rows even carry catalog_mapping_status), and mix identity is record-level (SprayRecord.catalog_mix_id, :154 — one mix per spray record, its chemical_items being that mix's components). Log identity therefore persists from P2 with no schema work, as long as consumers respect the level split. Plan items have no product_id column until Phase W — for plans, P2 identity means the canonical catalog name stored verbatim (string-level convergence), upgraded to a real FK when the web migration lands. Reports (P4) are identity-keyed for logs, name-keyed for plan-compliance deltas until W.

5Reports — the computation contract

All report math goes through fold() + totalFor(). The ad-hoc normalizer in report-service.ts:262-305 and its UNIT_ALIASES_TO_* sets are replaced by kernel calls (sets fold into the kernel's legacy parse table).

LensDefinitionRules
Per plot (एकूण)Σ totalFor(item, {areaAcres, waterLiters}) over the period, per product and per measureMass, volume, and count (pcs/packet/bag — today's UNIT_ALIASES_TO_COUNT rows) never merge into one number; count keeps its own bucket when units.ts is absorbed into the kernel. per_liter_water items need the record's water volume — if absent, the row is reported in a separate "concentration-only" bucket, never guessed. Custom (is_custom) products group under "Other".
Per acre (एकरी)per-plot ÷ farm.area (acres)Only computed when area is present and plausibly acres (see §8 hectare risk). Compliance delta ("prescribed 5 kg/acre · applied 4.2 kg/acre") requires a link: no plan_item_id exists on record items today — the one-tap-log flow (P3) writes an optional plan_item_id into the item JSON (same pattern as the existing optional catalog_product_id; no schema migration, items are JSONB). Records without it fall back to identity/name matching, rendered as "approximate" — never presented as a verified delta.
Per liter water (प्रति लिटर)Spray concentration view: Σ chemical mass/volume ÷ Σ water volume per spray event; period view = weighted meanOnly for spray records with water volume. ppm rows fold as mg/L natively. This is the PHI/residue-relevant lens — never averaged across events without weighting by water volume.
Nutrient ledger (kg N · P · K दिले)Σ product mass (kg) × declared composition % → per-nutrient kg, oxides converted to elemental via pinned factors (P₂O₅ ×0.4364 → P, K₂O ×0.8301 → K, …); views: per plot, per acre, per period, and between petiole testsAlready scaffolded end-to-end: catalog/warehouse composition → composition_snapshot + density_kg_per_l stamped on log items at submission (entry-log-submission.ts:172,266) → nutrient-flow-service.ts folds (consumed by petiole-trends today). Its toProductMassKg is the fourth drifting unit parser — P4 replaces it with kernel calls, preserving density/water-volume/ppm semantics (snapshot-locked first). Coverage is identity-bound and reported honestly: items without a composition snapshot are excluded and the UI says "nutrients from N% of applied quantity" (coveragePercent exists) — never padded. Display dual-basis: elemental computed (matches petiole/soil tests), bag-grade N-P₂O₅-K₂O shown alongside (the language bags and consultants speak). This is why Q7 items must carry composition.
PrecisionCompute at full precision, round only at render via format() (g under 1 kg, etc.). "≈" on every derived figure. No mid-pipeline rounding — the golden vectors (§9) assert exact intermediate values.

11Compliance layer — Annexure 5 + Annexure 9 close the loop

Two ICAR-NRC Grapes documents define the export-grape residue regime (APEDA / GrapeNet, EU export). Annexure-5 is the whitelist: ~80 chemicals with CIB&RC label claim — dose, EU-MRL, PHI days. Annexure-9 is the audit list: 278 chemicals the residue lab tests (per the 09 Oct 2025 revision), of which 164 sit at LOQ (0.01*) — zero tolerance, detection above LOQ rejects the export consignment. MRLs are harmonized across both (verified: Amisulbrom 0.50, Azoxystrobin 3.00, Cyazofamid 2.00). An active sibling plan already owns Annexure-5 compliance: docs/plans/2026-06-24-001-feat-grape-spray-compliance-plan.md — versioned chemical_label_sources / chemical_label_claims / chemical_label_claim_mrls tables, a reviewable import pipeline, a pure evaluator returning allowed | warning | blocked | unverified (target-, stage-, and application-count-aware), per-spray claim snapshots (historical truth), fail-closed harvest summaries, and version-and-supersede source updates. This section does not introduce a second compliance system. Everything below is re-scoped as extensions to that plan: its schema names replace the column sketch this section previously invented; its exact-formulation review stance ("no fuzzy auto-verification; ambiguous rows stay blocked") replaces the brand→active mapping table previously proposed here; its evaluator states replace this section's three-state guard. What this section adds that the sibling plan does not cover: the Annexure-9 monitored/zero-tolerance layer, the exporter spray-diary deliverable (it has only a summary ratio line), and the live-revision pinning below (the sibling plan is itself pinned to the superseded 17 Sep 2025 edition).
Why this elevates the whole plan
A spray log is not a diary entry — it is a line on an export compliance document. A ml→kg unit corruption or a free-text product name doesn't just skew a chart; it falsifies the audit trail an exporter relies on. The kernel's never-silent-fallback rule and SearchSelect's identity capture are compliance requirements, not code hygiene.

11.2 · Spray-time guard — consumes the June-24 evaluator, adds one input

The sibling plan's pure evaluator already returns allowed | warning | blocked | unverified from claim + date + harvest target + stage + prior applications. This plan adds the Annexure-9 monitored/zero-tolerance dataset as one more evaluator input and wires the result into SearchSelect at selection time (the evaluator's existing seam is pre-save):

Evaluator outcomeSearchSelect / form behavior
allowed (verified claim)Prefill label-claim dose chip + value; PHI days inline (feeds existing safe-to-spray matrix).
blocked-class: zero-tolerance (A9 LOQ, no label claim)Strong localized warning at selection and save: "export grapes: zero tolerance — consignment will fail residue test." Whether this maps to hard blocked or override-able warning is open question #5. Telemetry counter either way. Catching this at spray time saves the season; the lab catches it after harvest, when the lot is already lost.
unverified (unknown / custom / unmapped)Neutral "unverified for export" notice. Never blocks logging — an unlogged spray is worse than an unverified one. Fail-closed rule (sibling R6): unverified sprays make the season summary unverified, never silently omitted.

11.4 · Seasonal refresh discipline

Both annexures revise repeatedly within a season, not once a year: the PDFs reviewed for this plan (A5 17 Sep 2025, A9 09 Oct 2025) were already superseded by A5 rev. 03 Nov 2025 and A9 rev. 17 Jan 2026 on nrcgrapes.in at the time of writing — this plan itself hit the staleness failure mode it warns about. So did the sibling plan: its "first source edition" is pinned to the 17 Sep 2025 A5 — its Unit-2 import should target the 03 Nov 2025 revision instead. The mechanism is already right there (R10: additive, effective-dated, never overwrite — chemical_label_sources carries provenance); what this section adds is the operational rule: the import fetches the live documents from nrcgrapes.in at import time and records the revision it actually loaded. A farm operating on a superseded whitelist is a compliance bug of the same severity as a unit corruption — surfaced in §8 risks and open question #6.
