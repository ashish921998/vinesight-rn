Multi-Device Write Safety

Goal: same user account (one phone number) signed into 4+ mobile devices simultaneously, working correctly.  ·  Stack: React Native (Expo) + Supabase phone OTP + React Query.  ·  2026-06-03

TL;DR

AUTH  Already works. Supabase allows unlimited concurrent sessions per user by default. No code change needed — just verify a few dashboard settings (Part 1). The recent logout change to scope: 'local' was the one prerequisite, and it's done.

DATA  Not safe yet. The app uses client-side read-modify-write on shared fields. With 4 concurrent editors this silently loses updates and corrupts farm water levels. Fix is server-side atomic writes (Part 2 & 3) — realtime sync is not required for correctness.

Part 1 — Authentication: already supports 4+ devices

Auth is user-centric. Each device that completes OTP sign-in gets its own independent session + refresh token; there is no client-side device cap, and SecureStore is per-install so the four phones never share token storage.

There is no supabase/config.toml in the repo, so these live only in the Supabase Dashboard. If any are misconfigured, the 4-device requirement breaks regardless of code. Source: supabase.com/docs/guides/auth/sessions

  • Enforce single session per user → must be OFF. If ON, only the newest login survives; the other 3 devices get kicked.
  • Time-box user sessions → never/0 or long enough for your usage.
  • Inactivity timeout → never/0 or long; otherwise an idle device gets logged out.
  • Refresh token reuse interval → keep default 10s; do not lower aggressively or rotation false-positives can log devices out.
  • JWT expiry → keep sane (≥ 5 min, default 1h).

Part 2 — The four write-safety risks

All collisions live in two patterns: read-modify-write (read a value into the client, compute, write absolute result back) and upsert last-writer-wins. Pure inserts are safe. Severity reflects how silent and how damaging the corruption is.

1. Farm water level — silent corruption CRITICAL

Irrigation logging reads remaining_water from a stale client snapshot, adds a delta, and writes back the absolute result. Two devices reading the same starting value each overwrite the other — the tank level ends up reflecting only one irrigation, not both.

Snapshot built once per session: save-entry-log-session.ts:365

// entry-log-submission.ts:105-112  (read-modify-write)
const waterAdded     = duration * farm.system_discharge;
const currentWater   = farm.remaining_water ?? 0;            // ← stale read
const newWaterLevel  = Math.min(farm.total_tank_capacity, currentWater + waterAdded);
await submitters.updateWaterLevel({ farmId, remainingWater: newWaterLevel }); // ← absolute write
// use-farms.ts:384  (the absolute UPDATE — no concurrency guard)
.from(TABLES.FARMS)
.update({ remaining_water: remainingWater,
          water_calculation_updated_at: toSupabaseTimestampString(new Date()) })
.eq('id', farmId)
Failure: Tank at 1000 L. Device A logs irrigation +200; Device B simultaneously logs +150, both read 1000. A writes 1200, B writes 1150 (or vice versa). True value should be 1350. One irrigation is silently lost, and the running tank balance drifts permanently.

Same stale-read flaw also in the manual water sheet (water-level-sheet.tsx:122) and the failure rollback restores the stale value (save-entry-log-session.ts:127).

2. Daily note overwrite MEDIUM

Daily notes upsert on (farm_id, date). If two devices edit the same day's note, the second save replaces the first device's text wholesale — no merge, no warning.

// use-records.ts:704-714
.from(TABLES.DAILY_NOTES)
.upsert({ farm_id, season_id, date, notes: notes?.trim(), updated_at: ... },
        { onConflict: 'farm_id,date' })   // ← last writer wins, clobbers prior text

Less dangerous than #1 because it's visible — the user can notice the missing text and re-type. But it's the most likely day-to-day collision for 4 people on one farm.

3. Farm create — display_order collision LOW

New farms compute display_order client-side. There's retry logic, but four simultaneous creates can exhaust retries. Low impact: ordering glitch, not data loss.

4. Farm reorder — last-writer-wins LOW

Bulk reorder writes are inherently last-writer-wins unless the reorder_farms RPC carries a version check. Two devices reordering at once: one wins. Low impact: cosmetic, user-correctable.

Part 3 — Minimum fix to make 4 concurrent writers correct

The fix is not a React Query tweak and not realtime. It's moving stateful mutations server-side so the database does the read-modify-write atomically. Realtime would only improve freshness, which is a separate, optional nicety.

1

Atomic irrigation RPC fixes #1, highest value

Add a Postgres function that inserts the irrigation record and updates the water level as a delta, in one transaction. The DB computes the new level from its own current row, never a client snapshot.

create or replace function log_irrigation(
  p_farm_id bigint, p_date date, p_duration numeric, p_area numeric, ...)
returns jsonb language plpgsql security definer as $$
declare v_record irrigation_records; v_farm farms;
begin
  -- ownership enforced by RLS / auth.uid() = user_id
  insert into irrigation_records(farm_id, date, duration, area, ...)
    values (p_farm_id, p_date, p_duration, p_area, ...) returning * into v_record;

  update farms
     set remaining_water = least(total_tank_capacity,
                                 coalesce(remaining_water,0) + p_duration * system_discharge),
         water_calculation_updated_at = now()
   where id = p_farm_id
   returning * into v_farm;                          -- atomic delta, no stale read

  return jsonb_build_object('record', to_jsonb(v_record), 'farm', to_jsonb(v_farm));
end $$;

Then replace the insert-then-update path at entry-log-submission.ts:86-138 with a single supabase.rpc('log_irrigation', …). Drop the client-side compensating-delete and the stale rollback at save-entry-log-session.ts:127 — atomicity is now the DB's job. On success, invalidate queryKeys.farms.*.

2

Compare-and-swap for manual water set + daily notes fixes #2 and manual #1

For absolute writes that can't be expressed as a delta (manual water-level set, note edits), add an optimistic-concurrency guard: a water_version column (or reuse water_calculation_updated_at) and reject the write if it changed since the client read.

update farms set remaining_water = $new, water_calculation_updated_at = now()
 where id = $farmId and water_calculation_updated_at = $expectedTs;   -- 0 rows ⇒ stale, reject & refetch

For daily notes: same idea on daily_notes.updated_at, or merge instead of clobber. At minimum, detect the conflict and warn the user rather than silently overwriting (use-records.ts:704).

3

Version-checked reorder + create fixes #3, #4

Move display_order assignment fully server-side (sequence or RPC computing max+1 in-transaction) so concurrent creates can't collide; add a version guard to reorder_farms. Low priority — ordering glitches, not data loss.

4

(Optional) Realtime freshness UX, not correctness

Subscribe to Supabase Realtime on the user's rows and invalidate React Query caches on change, so devices see each other's writes in seconds instead of up to 5 min (query-cache.ts:11). Pure UX — once Phases 1-3 land, writes are already correct without it.
